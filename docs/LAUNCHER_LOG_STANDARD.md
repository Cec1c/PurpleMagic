# PurpleMagic 登录器日志规范

适用版本：**1.0.7 源码候选（外层 4 / 记录 3）**；兼容读取旧外层 2/3。整理日期：**2026-10-31**。适用对象：玩家、客服、论坛维护者及问题排查人员。

增强诊断用于记录登录器故障、游戏异常栈和游戏前台操作活动。玩家同意后开启，数据保存在本机，由玩家选择导出和分享。本规范描述当前登录器的实际行为；论坛接收日志时按本文的格式与解释约定对接。

## 1. 使用规则

| 项目 | 当前规则 |
| --- | --- |
| 入口 | 设置 → 增强诊断日志 |
| 默认状态 | 关闭；开启前显示说明，点击“同意并开启”后生效 |
| 操作方式 | 一个开关，正常启动游戏后自动记录 |
| 日志分组 | 每次游戏启动一份；双开分别记录，最多自动关联本客户端目录的两个游戏实例 |
| 本地保留 | 按启动时间保留最近 5 次；启动或更新失败也可形成诊断记录 |
| 文件上限 | 每份 10 MiB，即 10,485,760 字节；达到容量限制时标明截断 |
| 导出格式 | UTF-8 文本，扩展名 `.log`，每行一个 JSON 对象（JSONL） |
| 分享方式 | 玩家通过 Windows“另存为”导出，再自行选择接收方；登录器不会自动上传 |

同一游戏进程关闭后重新开启诊断，或重开登录器后恢复关联，在格式版本相同时续写原启动日志；升级到外层 4 后，旧格式日志封存，正在运行的进程创建新的日志段。新旧日志段都计入最近五份。游戏进程重新启动则创建新日志。关闭诊断后，已有日志仍可导出。

## 2. 同意说明与权限

开启时的现行说明如下：

> 开启期间会收集登录器和游戏的异常码、异常调用栈、故障地址、寄存器、内存页属性、模块版本与摘要，以及异常位置最多 64 字节的模块代码。还会记录游戏窗口处于前台时的玩家操作：方向键、按键次数、鼠标点击、移动与滚轮活动和焦点变化。
>
> 其他按键合并为次数，不记录按键文字、聊天内容、密码或 Token。日志只保存在本机，保留最近 5 次，可由你导出 .log 分享；不会自动上传。
>
> 异常采集会以调试方式关联游戏进程，异常发生时短暂暂停进程以读取调用栈。权限不足时可点击提升诊断权限，由 Windows 弹出 UAC 确认。关闭开关或退出登录器后停止采集。

“取消”保持关闭。“同意并开启”记录同意版本 `consentVersion=2`；旧版本已开启诊断的设置会迁移为关闭，重新同意后才启用扩大的采集范围。核心程序也校验同意版本。此次诊断同意升级不改变反作弊同意记录。

采集先使用当前权限。系统拒绝关联时，界面提供“提升诊断权限”按钮，玩家点击后才请求 UAC。只有诊断辅助进程申请提升；取消后继续普通采集，不反复自动弹窗。

关闭开关、切换客户端目录或退出登录器会刷新记录并脱离游戏。辅助进程同时监测父进程退出；脱离时不主动结束游戏，不设置持久调试器或 WER 注册表项。

## 3. 采集内容

| 类别 | 记录内容 | 采集方式与边界 |
| --- | --- | --- |
| 登录器运行 | 更新结果、客户端与频道检查、账号 API 状态码、启动尝试、游戏进程创建及退出 | 保存事件与数值状态；登录前更新失败也可导出 |
| 基础性能 | 游戏进程累计 CPU 时间、工作集、私有内存、虚拟空间占用、系统 commit 总量/上限、32/64 位及 LAA 标记、窗口响应状态 | 每秒摘要；当前没有逐帧耗时数据 |
| 登录器异常 | 错误类别、HResult、可用的系统或 HTTP 数值错误码、内部异常链、方法栈 | 最多 6 层异常，每层最多 32 帧；缺少方法元数据时使用 `unknown` 等占位 |
| 游戏异常 | 原始异常记录、访问类型与故障地址、首次或未处理通知、线程 ID、原始寄存器、模块与地址栈、有界页属性和代码窗口 | Windows 调试接口；单次最多 64 帧，不生成内存转储或下载符号 |
| 玩家操作 | 方向键按下次数、其他键匿名次数、鼠标按钮、移动活动、滚轮和焦点变化 | 只统计目标游戏处于前台时的输入；约每秒汇总，有活动才输出计数 |
| AT-5T 专项 | 适配场景中的角色、载具、规则、逻辑输入状态、游戏世界坐标及计算距离 | 仅完整 EXE 哈希匹配已验证布局时自动启用；单轮最长 30 秒，目标间隔 5 ms，日志记录实际耗时 |
| 版本与质量 | 登录器版本、模块版本、EXE/PVF 实际 SHA256、预期 PVF SHA256、签名发布序号、standard/anticheat 发布通道、缺失和截断信息 | 用于确认资源与诊断能力是否匹配 |

AT-5T 专项当前使用 `at5t-readonly-1`，已验证布局为 V135、V141，精确哈希见[实现说明](LAUNCHER_DIAGNOSTICS.md#字段与版本)。其他 EXE 使用基础诊断及 Windows 通用异常、操作能力，专项标记为不支持。

玩家操作计数字段如下：

| 字段 | 含义 |
| --- | --- |
| `left` / `up` / `right` / `down` | 对应方向键的按下次数 |
| `keyboard` | 其他按键合并后的匿名按下次数 |
| `mouse_left` / `mouse_right` / `mouse_middle` / `mouse_extra` | 鼠标对应按钮的按下次数 |
| `mouse_motion` | 存在鼠标移动的输入事件次数，不含坐标或移动距离 |
| `wheel` | 滚轮活动量，按系统增量的绝对值除以 120 汇总 |
| `foreground` | 焦点变化记录中的状态，1 为游戏前台，0 为离开前台 |

按住键产生的重复按下事件会合并。各秒汇总不能恢复原始按键顺序，也不能说明某个技能是否命中、任务是否完成或物品是否到账。

## 4. 数据范围

导出只使用允许的字段。密码、Token、账号内容、完整启动参数、安装路径、窗口标题、聊天、输入文字、字母与数字键的具体键值、鼠标坐标均不进入日志。托管异常消息正文、异常 `Data`、文件路径、URL 和方法调用参数值也不导出；Windows 原生异常参数、寄存器及最多 64 字节模块代码属于新增现场证据，可能包含程序内部标识；不读取任意堆内容，不生成 dump。

日志包含运行时间、进程和线程标识、资源哈希，以及适配专项中的技术状态和游戏世界坐标。玩家可在分享前用文本编辑器查看内容。

当前未接入服务端业务事件和服务端时钟校准，也没有客户端逐帧耗时、完整函数执行顺序或游戏内部距离函数的实际返回值。末尾汇总通过 `missing` 和 `server_events_connected=false` 明确这些缺项。

## 5. 保存与导出

记录保存在用户状态目录的 `diagnostics/logs/`。每次启动的日志配套一个本地索引；索引用于恢复和列出日志，玩家分享导出的 `.log` 即可。

- 约每秒提交一批完整记录；游戏退出、关闭诊断、退出登录器和导出时刷新。
- 每实例采用有界缓存和写入队列。普通采样达到容量限制后，为异常和近期操作预留空间，并为最终未处理异常及汇总继续预留容量。
- 中断写入恢复到最近持久化索引对应的完整记录，导出不保留半行 JSON。
- 运行中的日志可以导出，内容截至当次刷新；之后的活动需要再次导出。
- “另存为”取消时不写文件；覆盖已有文件由原生窗口确认，完整写入成功后再替换目标。
- 最近 5 次的清理按启动时间排序，不按导出时间或保留天数排序；玩家已导出的副本由玩家自行管理。

## 6. 文件格式与兼容

新创建日志的外层版本为 `schema_version=4`，每条中间记录显式携带 `record_version=3`。每份导出文件按以下顺序组成：

| 位置 | `type` | 主要内容 |
| --- | --- | --- |
| 第一行 | `log_header` | 创建时的版本信息、会话及初始摘要 |
| 中间各行 | `identity`、`event`、`performance`、`scene`、`sample`、`exception` | 事件、采样与异常证据 |
| 最后一行 | `log_summary` | 本次导出时的版本、完整哈希、数量及质量汇总 |

头与尾的公共字段为 `schema_version`、`collector_version`、`module_version`、`log`。`log` 下包含 `summary`、`started_utc`、`ended_utc`、`last_sequence`、`last_time`、`bytes`、`schema_version`。以**末尾** `log.summary` 作为最终汇总；其中 `records` 只统计中间记录行，不含头尾。`ended_utc` 表示最近保存时间，正在运行的日志也有该值，不能单凭它认定游戏已经退出。

历史日志允许头部 2、末尾 3。新外层 4 的头尾必须一致，不向旧流追加新记录。旧文件原记录继续可导出。新格式遵循 [envelope-v4.schema.json](diagnostics/envelope-v4.schema.json) 与 [record-v3.schema.json](diagnostics/record-v3.schema.json)，顶层和证据对象拒绝未声明字段；外层与记录使用不同版本编号。

| 中间记录字段 | 约定 |
| --- | --- |
| `session_id` | 32 位小写十六进制会话 ID；同一文件内一致 |
| `sequence` | 从正整数开始递增，允许因丢样或截断出现间隔 |
| `utc` / `monotonic_ms` | UTC 时间与会话单调时间；单调时间不得倒退 |
| `type` / `module` | 记录类别与来源模块 |
| `read_ms` | 读取或采集处理耗时，单位毫秒 |
| `quality` | 整条记录质量：`ok`、`partial`、`unstable`、`read_failed`、`dropped` |
| `fields` | 各数值字段的 `value`、`status` 及可选 `reason` |
| `reason` | 事件或采样原因码，例如 `player_operations`、`game_focus` |
| `base_sequence` | 专项差量快照关联的完整快照序号 |
| `evidence` | 可选异常证据，类别为 `managed_exception`、`native_exception` 或 `module_identity` |

单字段 `status` 为 `ok` 时 `value` 是数值；`not_applicable`、`unsupported`、`read_failed`、`unstable` 时为 `null`。这些状态分别表示不适用、不支持、读取失败或采样期间变化，不能统一转换成 0。完整专项快照至少每秒输出一次；解析差量前须找到对应完整快照。

异常辅助进程还提供 `fields.observed_unix_ms`，表示实际采集时的 Unix 毫秒时间。它与主日志接收并编排记录的时间不同；比较跨来源时序时应同时保留。

## 7. 异常与质量信息的解读

| 信息 | 解读约定 |
| --- | --- |
| `first_chance=1` | 异常首次通知，游戏自身可能处理后继续运行；不能直接标记为闪退 |
| `first_chance=0` | 未处理异常通知；结合进程退出、退出码和玩家描述判断影响 |
| 游戏异常采集额度 | 每个采集器最多 16 次首次通知、2 次未处理通知；后者使用独立额度 |
| 栈中的模块与偏移 | 用于定位代码位置；需匹配同一 EXE/模块版本，不能只凭模块名推断根因 |
| `errors` | 诊断记录中部分失败、不稳定或读取失败的累计计数，不等于游戏崩溃次数 |
| `dropped` / `overwritten` | 前者为丢弃计数，后者为环形缓存覆盖累计；`overwritten` 不表示导出缺了相同行数 |
| `truncated=true` | 文件因容量限制省略了部分内容；保留的记录仍可分析 |
| `missing` | 未采集、不支持或失败的能力与字段；缺记录不代表该事件没有发生 |
| `correlation_id` | 当前用于本地会话关联；不能据此宣称已与服务端日志完成关联 |

日志包含技术诊断数据，建议私下交给排查人员。现有分析器的 `verified=true` 表示结构和内部一致性检查通过；文件 SHA256 用于比对文件内容，两者均不证明玩家提交的日志由可信来源签名或未经修改。

## 8. 论坛接收与展示约定

本节供论坛维护者对接，论坛功能落地情况由论坛项目单独记录。

1. 让玩家自主选择 `.log` 附件，并说明附件的可见范围。登录器的采集同意与论坛的上传分享是两个操作。
2. 以 10 MiB 为单文件接收上限，按 UTF-8 JSONL 检查内容；保留原文件供下载，展示日志文字时进行转义。
3. 先检查外层版本、头尾、会话 ID、序号、单调时间和记录数，再读取中间记录及差量关联。结构损坏与有明确截断标记的有效日志分别展示。
4. 摘要优先展示登录器版本、游戏 EXE/PVF 哈希、时间范围、异常、操作活动，以及 `missing`、丢样和截断信息。正确处理首次异常与未处理异常的区别。
5. 附件旁保留玩家填写的现象、发生时间和复现步骤。操作次数只能描述活动；任务、奖励、伤害等业务结果需要对应业务证据。
6. 向玩家索取导出的日志即可，不要求提供密码、Token、完整启动参数或聊天内容。遇到新版本或未知字段时保留原文，并明确解析能力范围。

仓库提供离线分析入口：

```powershell
python -m pip install -r scripts/diagnostics/requirements.txt
python scripts/analyze_diagnostics.py "玩家导出的文件.log"
```

分析器兼容外层版本 2/3/4，也支持历史诊断 ZIP。`critical_events` 保留全部已记录异常阶段、退出和采集失败；`timeline` 另保留首尾及异常附近普通事件，`omitted_event_ranges` 明示省略范围。一次 first-chance 与随后未处理阶段不会计成两次崩溃。后续观察器失败不自动作为崩溃原因。外层 4 同时进行严格 Schema 校验。当前登录器的导出与论坛对接格式为 `.log`。

## 9. 验证状态与维护依据

1.0.7 为本次源码候选，发布、游戏实测与源码验证分别记录。自动化覆盖核心逻辑、存储与导出、同意框及权限按钮；实际 Windows x86/x64 隔离子进程验证了异常采栈、原异常处理、父进程退出后脱离及 NativeAOT 导出。验证细项见[验证记录](diagnostics/VALIDATION.md)，其中旧候选版本与发布前状态按历史保留。

调试关联会使游戏的 `IsDebuggerPresent` 为真，采栈时会短暂停住游戏。正式游戏反调试兼容、真实 UAC 操作、玩家输入、原生另存为点击和长时间运行性能仍需实机验收。

维护依据：[实现说明](LAUNCHER_DIAGNOSTICS.md)、[记录 Schema](diagnostics/record-v3.schema.json)、[原生证据契约](diagnostics/NATIVE_EVIDENCE_V4.md)、[诊断源码](../launcher/Engine/Diagnostics/)、[开启与导出界面](../launcher/Flutter/lib/diagnostics_panel.dart)、[分析器](../scripts/analyze_diagnostics.py)。采集范围、同意版本或文件格式变化时同步修订本规范，并通知接收日志的论坛维护者。
