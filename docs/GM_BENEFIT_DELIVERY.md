# 福利规则与发放进度

福利规则是独立入口 `/console/#benefits`，不依赖当前账号或角色。可创建金币、点券和指定道具规则、暂停和恢复自动发放、查询发放情况。沿用兰紫界面与既有规则、领取范围和永久回执。

## 发放详情

`GET /api/v1/benefits/{id}/recipients` 直接读取当前收件范围和永久发放回执，使用签名分页游标。每页最多访问五个账号，返回不超过请求 `limit` 的记录；空页也可能带下一页游标。角色选择仅读取基础资料，发放事务仍重新锁定并检查完整权威记录。

打开详情后自动串行接续分页，包括带游标的空页。默认只列未发放对象（含失败项），统计未发放数量；成功对象收进默认折叠的「已成功发放」，范围外对象另行折叠。查询期间标注「已查询范围」，读取完成后显示本轮完整统计。关闭窗口或刷新会取消旧请求，网络中断保留已加载结果并可从失败分片继续。

点券展示实际收件角色、到账金额和前后余额；角色删除后仍可显示账号的永久回执。暂停规则保留范围及回执。查看和刷新详情不调用创建全量预览任务的 POST 接口，也不触发发奖。

`POST /api/v1/benefits/{id}/preview` 保留给需要固定名单的既有管理操作，不再承担详情查询。既有任务接口和人工批次契约保持。

## 自动发放

外部 GM 使用私有 `POST /api/internal/gateway/v1/scan-v2`。位置包括注册账号序号、角色 ID、规则 ID，可在大账号内部续扫。每次最多访问五个账号、尝试十次投递，每次投递有独立四秒上下文，单次扫描总上下文为二十秒。剩余时间不足时返回当前位置；单个失败继续推进，下轮完整扫描重试。

后台默认每三小时完成一轮校验。首次启动立即开始，之后从本轮完成时计时；启用或更新规则会安排立即校验。`scanSeconds` 是一轮内分片之间的调度间隔（5–3600 秒），不应设为三小时。每轮覆盖所有账号，因此既包含新账号的首个角色，也包含老账号中新建的角色；仍按规则原有范围决定资格。没有角色的账号在创建角色后的校验中领取。

游标、当前进度、上次完成与下次时间保存在现有队列文件的单个 `reconciliation` 记录中，重启续查；不会按轮次无限创建补发任务。认证接口 `GET /api/v1/benefits/reconciliation` 提供状态，福利页每十五秒回读。关闭页面不影响后台。失败对象下轮重试，也可使用原有「补发未收到」。

扫描先读取永久回执，跳过已成功项，避免重复进入昂贵的写事务。实际发放仍使用原有账号锁、邮箱/钱包事务及幂等键；账号奖励在同账号多个角色之间只发一次。删除邮件、进程重启、暂停恢复都不清除永久回执。没有新增数据库表。

## PVF 更新后的连续发放

PVF 全文件哈希改变后，索引仍须按新的批准哈希重建。福利扫描核对新旧单个物品的脚本哈希、完整定义、投影附件和数量。全部一致时，自动将原规则绑定到当前批准的 PVF，保留原规则 ID、范围、选项和首次回执指纹，记录核对历史后继续发放。新旧物品定义不同或旧规则缺少定义证据时，保留待发并显示「物品版本待核对」，通过既有 PVF 核对接口确认后续发。不会把旧领取记录当成新一轮资格。

网关日志保留请求编号和错误原因；扫描失败记录账号游标、角色与规则 ID。旧版扫描端点保留兼容，但正式外部调度器使用 v2。发布需要同时更新 GMService 和 PlayerGateway，并保留现有队列、会话、PVF 代次及回执。旧规则中的待发对象由新扫描器自动继续，无须重建规则或人工重发。

## 验证

- 一次性数据库覆盖单/双分片、多账号分页、大账号内部续扫、单角色失败不阻塞后续名单、故障恢复、重扫去重、账号点券只入账一次、删除邮件后回执查询、暂停与未来角色。
- 页面分页由请求测试和 React 实际渲染测试覆盖自动接续、空页、取消、失败恢复、成功默认折叠及部分统计；RPA 保持停止。
- 定时任务以注入时间验证三小时间隔、重启续查、响应丢失、规则启用与并发状态读取；一次性 MariaDB + 实际 HTTP 验证新账号/角色、PVF 核对和永久回执。
- 正式数据库上的新分页读取仅用于只读耗时与回执核对。生产补发和最终回读由部署交接执行。


## 手动补发与增量写入（2026-10-21）

规则列表和发放详情均提供“补发未收到”。无需选择角色；确认时读取原规则的奖励、范围和版本，后台逐页处理本次开始前已创建的对象。暂停规则须先启用。再次补发跳过原永久回执，账号点券只入账一次，金币和道具遵循原领取次数。

外部 GM 的 `POST /api/v1/benefits/{id}/redelivery` 要求确认、规则版本及幂等请求编号，先将补发任务原子保存到现有队列文件，再由后台处理。`GET` 同路径返回最新一轮进度：已检查、确认已收到（含原已发）、跳过、失败及最多十个失败样本。页面关闭不影响处理；详情打开时每两秒更新进度。网络失败保留游标并重试；规则暂停、修订或 PVF 代次变化会停止旧任务。

队列调用私有 `/api/internal/gateway/v1/benefits/{id}/redelivery`，每次最多五账号读取和一个收件对象、四秒投递事务。成功页的游标与计数一起落盘。若事务已提交但响应丢失，重启后重新读取原永久回执，计数归入“确认已收到”。查看详情不创建任务；补发不调用全服 `preview`。

MySQL 账号/邮箱事务新增邮件追加能力：锁定原角色、账号和邮箱父行，只插入新邮件及附件，不删除重写整箱旧邮件。钱包和发放回执仅更新对应的元数据键，继续同事务提交；其他邮箱操作的聚合存取接口保留。手动补发、自动扫描和新角色奖励使用同一投递路径。

含未来角色的已启用规则由自动扫描持续覆盖：新账号无角色时等待收件角色；首个角色创建后发放；同账号后续角色不重复领取账号点券，但可各自领取按角色发放的金币和道具。未包含未来角色的规则保持原截止范围。

验证包括：单/双分片、104 封旧邮件的逐条读回、禁止旧行删除的数据库触发器、失败后补齐、投递已提交但响应丢失、队列重启、重复提交、自动扫描与手动补发并发、暂停/版本/PVF变化，以及新账号首个/第二个角色和老账号新角色。浏览器验收在关闭自动扫描的隔离服务中实际点击补发，并核对钱包和道具数量；随后启用扫描验证新角色自动领取。
